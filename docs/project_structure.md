# Repository structure overview

This document is the architectural map of the current repository. It reflects
the responsibility-based refactor merged at `ea531f6` and explains how the
active implementation, literature lineage, experiments, evidence, presentation,
and historical compatibility layers fit together.

The repository is intentionally more than a software package. It is maintained
as a **living computational literature review**: published methods are mapped to
code, experimental reproductions are kept distinct from repository extensions,
and historically meaningful paths remain available when they document how the
research interpretation evolved.

For the paper-to-code history, see
[Living computational literature review](living_literature_review/README.md).
For study-level status, see [Study tracker](living_literature_review/studies.md).

```text
│   └── living_literature_review/     # paper → code → evidence lineage
├── notebooks/                        # early exploratory/reproduction notebooks

├── papers/                           # core local source PDFs used by the project
├── presentations/                    # progress-review presentation artifacts
├── scripts/                          # command-line experiment runners
├── src/                              # canonical research implementation
├── static/                           # Flask page styles and browser assets
├── templates/                        # Flask/Jinja result views
├── tests/                            # domain-grouped verification and regressions
├── app.py                            # stable Flask launch entry point

└── requirements-*.txt                # dashboard, support and test dependencies
```

The most important distinction is:

- `src/` contains reusable research implementation;
- `scripts/` orchestrates experiments;
- `outputs/` stores evidence generated by those experiments;
- `docs/` records methodological interpretation and provenance;
- `papers/` records the core literature sources;
- `archive/` preserves superseded workflows without making them canonical.

## 3. What each layer owns

| Layer | Responsibility | Typical inputs | Typical outputs |
| --- | --- | --- | --- |
| `src/bci` | EEG/BCI loading, trial extraction, FBCSP feature construction, dataset protocols | raw/prepared EEG and labels | trial matrices, FBCSP features, development/evaluation splits |
| `src/detection` | covariate-shift screening and statistical validation | feature streams | Stage-I warnings, Stage-II confirmations/rejections |
| `src/adaptation` | classifier update mechanisms and update policies | classifier, detector evidence, labelled or pseudo-labelled observations | predictions, update events, adapted classifier |
| `src/experiments` | paper-specific experimental orchestration | generators, detectors, configs | paper-specific reproduction records |
| `src/reporting` | metrics and paper-style tables | detector/adaptation outputs | CSV/Markdown summaries |
| `src/simulation` | controlled synthetic streams | seeds and shift parameters | known-change streams for detector analysis |
| `src/web` | presentation of generated evidence | committed/generated result files | Flask pages and interactive result views |
| `src/support` | repository/proposal assistance utilities | local indexed text | support/RAG responses |

The web layer is intentionally downstream of the research computation. It
should present generated evidence rather than silently rerun EEG/CSE pipelines.

## 4. End-to-end research flow

The main computational path is:

```text
raw EEG / prepared features / synthetic streams
                    │
                    ▼
            src/bci or src/simulation
                    │
                    ▼
          feature representation
       FBCSP → PCA / monitored signals
                    │
                    ▼
         src/detection/stage1
       EWMA candidate shift warnings
                    │
                    ▼
         src/detection/stage2
      K-S / Hotelling validation paths
                    │
                    ▼
           src/adaptation
   supervised or transductive update logic
                    │
                    ▼
          src/reporting + outputs
                    │
                    ▼
              src/web
```

Not every experiment uses every layer. For example, the Raza et al. (2015)
synthetic reproduction can stop after detection/reporting, while the
Chowdhury/Raza adaptive-learning work continues into classifier adaptation.

## 6. Adaptation structure after the latest refactor

The adaptation layer is deliberately split by information regime and research
lineage:

```text
supervised.py
    │
    ├── synchronous true labels
    └── Chowdhury-style append-and-retrain
            │
            ▼
pseudo_labelling.py
    │
    └── PWKNN label/confidence estimation
            │
            ▼
transductive.py
    │
    ├── labelled calibration set
    ├── unlabelled evaluation stream
    └── confidence-gated knowledge-base growth
            │
            ▼
evaluation.py
    └── ground truth enters only after the online run for scoring
```

`policies.py` is orthogonal to those information regimes: it decides *when*
an update should be attempted.

`ensemble/bagging.py` is a passive classifier-comparison baseline. It should
not be described as the still-unimplemented dynamic CSE-UAEL ensemble.

## 7. Stage-II structure after the latest refactor

The repository intentionally preserves multiple Stage-II interpretations:

| Canonical module | Comparison represented |
| --- | --- |
| `stage2/ks.py` | univariate K-S validation pathway |
| `stage2/training_reference_hotelling.py` | current observation versus training-reference interpretation |
| `stage2/paper_two_sample_hotelling.py` | equal-window two-sample paper-aligned interpretation |
| `stage2/retrospective_hotelling.py` | configurable retrospective multivariate-window validator |

These implementations should not be collapsed into one generic
"Hotelling test" because they compare different statistical objects and have
different timing semantics.

## 8. Compatibility and provenance layer

Several files still exist directly under `src/`, including:

```text
src/cse.py
src/ewma.py
src/fbcsp.py
src/bci_data.py
src/bci_features.py
src/cse_algorithm1_stage_2.py
src/cse_paper_stage_2.py
src/multivariate_stage_2.py
src/table1_reproduction.py
src/tssd_ewma.py
...
```

These are retained where practical as **compatibility/provenance shims**.

New development should target the structured packages, for example:

```python
from src.bci.data import load_bci_competition_iv_2a_session
from src.bci.datasets.dataset2a import extract_dataset_2a_trials
from src.detection import CSEConfig, run_cse
from src.detection.stage1 import fit_sd_ewma
from src.detection.stage2 import validate_algorithm1_alarms
from src.adaptation.transductive import run_transductive_adaptation
from src.reporting.table1 import Table1Row
```

Historical imports remain useful because they make older notebooks and
milestone commits reproducible. Compatibility tests verify that key old paths
resolve to the same canonical objects.

A useful rule is:

> reusable method code belongs under `src/`; experiment-specific sequencing
> belongs under `scripts/` or `src/experiments/`.

## 10. Evidence and outputs

`outputs/` is part of the research record rather than an interchangeable cache.

Important groups currently include:

- `outputs/metrics/bci_table1_*`: BCI Table-1 reproduction/comparison;
- `outputs/metrics/paper2015/`: synthetic detector reproduction evidence;
- `outputs/metrics/bagging_*`: passive classifier/ensemble comparisons;
- `outputs/complementary*/`: score/residual monitoring experiments.

When a later output uses changed assumptions, the earlier result may remain if
it documents a meaningful methodological milestone. The provenance policy
defines when evidence should be preserved, superseded, or archived.

## 11. Tests

Tests are grouped by responsibility:

```text
tests/
├── adaptation/
├── bci/
├── cli/
├── compatibility/
├── detection/
├── experiments/
├── reporting/
├── simulation/
├── support/
└── web/
```

`tests/compatibility/` is particularly important for the living-review model:
it prevents structural cleanup from silently breaking historical import paths.

GitHub Actions runs the repository pytest suite from
`.github/workflows/tests.yml`.

## 12. Web/presentation structure

The browser interface is split across:

- `src/web/`: route/data-model code;
- `templates/`: Jinja pages;
- `static/`: CSS and JavaScript;
- `app.py`: stable launch entry point.

Current pages cover the research home, Table-1 dashboard, Dataset-2A feature
view, local Dataset-2A/2B exploratory distributions, Chowdhury metadata,
complementary monitoring, Diethe experiments, support, and test-result views.

## 14. Architectural principle

The repository should continue to evolve according to this rule:

```text
paper / research question
        ↓
explicit computational interpretation
        ↓
canonical implementation
        ↓
experiment runner
        ↓
saved evidence
        ↓
documentation of result, discrepancy or limitation
```

Structural refactors should improve clarity without erasing the methodological
history needed to explain how the PhD implementation developed.
